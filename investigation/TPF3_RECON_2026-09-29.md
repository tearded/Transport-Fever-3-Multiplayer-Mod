# TPF3 release-day static recon -- 2026-09-29

Transport Fever 3 released today. This is the release-day investigation
[docs/DAY_ONE.md](../docs/DAY_ONE.md) calls for, done **statically**: the
executable was indexed with `tools/tpfre` (D14) and the game's own Teal
declarations (`.d.tl`) read. Nothing here was run in the game; the game was
never launched or modified from automation. The in-game measurements
DAY_ONE lists (determinism, hook feasibility, saves) are still to do.

Labels ([DAY_ONE.md](../docs/DAY_ONE.md)):
- **CONFIRMED-static**: named by the binary's own RTTI or assert strings,
  or declared in the game's `.d.tl`. Strong, but not yet seen live, so not
  the full CONFIRMED ("consistent with live behaviour") until MEASURED.
- **INFERRED**: concluded from decompiled code shape, not a name.
- **DOCUMENTED**: from Urban Games' reference / the on-disk declarations
  (see [TF3_OFFICIAL_API_2026-09-29.md](TF3_OFFICIAL_API_2026-09-29.md)).

## Naming: no `__FUNCSIG__`, lean on RTTI and source files

The single biggest change from TPF2 for RE: **TF3's release build carries
almost no `__FUNCSIG__` assert strings.** 23 funcsig strings name 16
functions (TPF2 had ~88,000 references). So the TPF2 naming pipeline barely
applies. Naming instead comes from, in order of use here:

- **RTTI**: 14,674 type descriptors, **7,947 vtables, 46,561 slots**. Class
  names and virtual methods are recoverable (`Class::vftable`, `Class::vfN`).
  This carried most of the findings below.
- **`__FILE__` source paths**: 906 file-assert strings attribute ~38k
  functions to a `.cpp`; `tpfre q DB file <name>.cpp` groups a subsystem.
- **luabridge**: the whole `api.*` Lua surface binds through luabridge, so a
  factory's Lua-name string walks to its native code (below).

`tpfre` indexes the 136,538 functions in ~2.7 s and answers `class`,
`vtable`, `file`, `str`, `whois`, `callers`, `xrefs` queries; that is the
release-day workflow now, not funcsig names.

## The command pipeline (CONFIRMED-static)

Every player or script action becomes a `Command` applied on the sim
thread. This is the capture's target (HOOKS.md, "The command pipeline").

- **Enqueue / cancel choke point: `CommandList::Add` @ `0x9d29c0`**
  (`commandlist.cpp`, RTTI-named). Signature from RTTI:
  `Connection Add(Command, std::function<void(Command const&)>, weak_ptr<CmdProgress>)`.
  It appends the 0x38-byte `Command` by value to a `vector<Command>` and
  returns a **`Connection`** -- the only handle by which a queued command
  can be cancelled. ~40 direct callers: every UI action functor and the
  scripting bridge.
- **Drain: `CommandList::Swap` @ `0x9d2d20`**, called from **`CGame::Sync`
  @ `0x11f650`** at the step boundary, double-buffers the accumulated
  commands out and records the lockstep ledger (`m_replicateTimes` /
  `m_commandTimes` / `m_stepTimes`, exposed to Lua as
  `getReplicateTimes` / `getCommandTimes` / `getCoreStepTimes`).
- **Apply: `sub_9e1c10`** ("Simulation Thread: Apply Command",
  `apply_command.cpp`) per command, via the dispatcher **`sub_9d7350`** --
  a jump table `[kind*4 + 0x9d8bbc]` keyed by an integer command-kind.
  After apply it writes the result byte to `Command+0x30` and fires the
  completion callback; the Lua callback (`sub_e299f0`) drops it if the Lua
  state died ("Skipped command callback due to destroyed lua state").
- **`Command` layout (INFERRED from consistent codegen):** 0x38 bytes, no
  vtable. `+0x00` payload pointer, whose **command-kind enum byte is at
  `payload+0x9b8`** (the jump-table selector); `+0x08/+0x10/+0x18` a vector
  of 16-byte affected-entity/result entries; `+0x20/+0x28` the refcounted
  callback / `CmdProgress`; `+0x30` the result status byte. Every command
  carries a **`playerEntity`**, asserted non-empty in `make_command.cpp`
  (`0x9ebc49`).
- **The Lua binding: `SetupCommandInterface` @ `0xe38ae0`** builds the
  whole `api.cmd.*` table (61 factories + `sendCommand`), reached from the
  master API registrar `sub_1087b40` (which calls ~19 `Setup*Interface`
  siblings, one per `api.*` sub-table). The real builders are in
  `make_command.cpp` (`0x9e97a0`-`0x9ee6f0`). Script replays enter through
  `sendCommand` (`sub_e10f50`) / this interface and reach the **same**
  `Add`.
- **Script->native factory map (partial).** From a factory's Lua-name
  string, `xrefs` it (all land in `SetupCommandInterface`), `dis` the
  registration block: 7 "bespoke" factories resolve to a distinct native
  binding (e.g. `makeGameAddPlayerCmd` -> `sub_e1d660` -> builder
  `sub_9ea910`); the other 54 share one generic `sendCommand` closure and
  have no distinct native RVA at the Lua layer (their identity is a runtime
  field-descriptor + name). To capture generically, hook `Add` (or the
  shared enqueue funnel `sub_e42470`, 62 callers) rather than per factory.

**Open, to reconcile (two agents disagreed):** whether
`DeferredCommandBuffer` (vtable `0x36dcac8`, 18 slots, `builderrenderer.cpp`)
is the world-command queue or a **UI/GPU render** command buffer. The
evidence (its class family beside `VulkanCommandBuffer`, its 24-byte
tag+float draw records) points to **rendering**, with `CommandList` being
the real world queue; but the enqueue funnel `sub_e42470` was also read as
targeting it. Resolve before choosing the capture hook: confirm
`CommandList::Add` (`0x9d29c0`) is the world path and `DeferredCommandBuffer`
is not.

**For the capture design:**
- One hook at `CommandList::Add` catches every command, player or script;
  it is also the only cancel point (returns the `Connection`).
- `playerEntity` on each command attributes it to a player -- useful for
  companies mode. (`makeWorldBuildProposalCmd`'s `playerInitiated` does not
  tell a player's build from a script replay: the scripts act on it; see
  the second pass.)
- The callback contract (a `std::function<void(Command const&)>` plus a
  `weak_ptr<CmdProgress>`, results returned in the `Command` itself) is
  load-bearing, as on TPF2: a cancelled or replayed command's callback must
  still be honoured or the tool hangs (HOOKS.md).

## The simulation clock (CONFIRMED-static)

Intact and the same shape as TPF2; only offsets moved.

- **`CGame::RunGameSimLoop` @ `0x11e210`** runs on a dedicated **"Simulation
  Thread"** (created in `sub_116d50`), QPC-timed, mutex/condvar handshake
  with the main thread.
- **`GameSim::Step` @ `0x159390`** is the per-frame advance; inside, it runs
  `max(speedSteps, pendingBudget)` sub-steps, each calling the ECS engine
  advance `sub_2bb8a50(engine, dt)`.
- **Speed is an integer**, from `ecs::component::GameSpeed` (`+0x04`), read
  by `CGameTime::GetSpeed` @ `0x2a95a0`. Pause is speed 0 (no separate
  boolean; the loop runs 0 sub-steps). Matches
  `makeGameSetSpeedCmd(speedup: integer)`.
- **Two game states, swapped each frame -- present.** `CGame+0x1f0` ->
  `m_data`: `+0x78 gameStates[2]`, `+0x88 gameSims[2]`, `+0x98 simIdx`.
  **`GameState::Replicate` @ `0x255de0`** copies the simulated state into
  the other buffer each frame (via `ecs::Engine::Replicate` @ `0x2bb78f0`);
  the UI reads the finished state through `UI::GameStateProvider`. Same
  architecture as TPF2's `CGame+0x168`.
- **A ready-made lockstep primitive.** `makeGamePerformSimulationStepsCmd`
  (a `Cmd.debug` factory) applies at `0x9d894c` as
  `lock add [0x403b8e0], N` -- an atomic global step budget that
  `GameSim::Step` drains (`xchg`, clamp to 64/frame, carry the remainder).
  So the **step gate may need no code patch**: set speed 0 and feed steps
  through this command. Its only writers are the applier, the consumer in
  `GameSim::Step`, and a debug panel. This is the cleanest gate found; the
  fallback is hooking `GameSim::Step` entry on the sim thread.

Struct offsets (from asserts/code): `GameState +0x18 ecs::Engine*`,
`+0x28 CGameTime*`, `+0x208/+0x20c` step/tick counters (copied by
Replicate); `GameTime +0x00` int64 counter; `GameSpeed +0x04` speed.

## Players and companies (CONFIRMED-static + DOCUMENTED)

Settles the separate-players question with strong evidence: **companies
mode is viable, and cleaner than TPF2's.** PLAN.md Part 3's companies mode
has a native path; whether the project ships it stays the owner's.

- **A player is an ordinary ECS entity.** `createPlayer` (`sub_cceee0`,
  `apply_command.cpp`) makes an entity and attaches a fixed component set:
  `Player` (`headquarters: Entity`, initialised to -1),
  `Name`, `Color`, `Account` (`balance`, `loan` -- money is per player) and
  `LogBook` (journal). Ownership is the `PlayerOwned` component
  (`{player: Entity}`). Component types `PLAYER`, `PLAYER_OWNED`, `ACCOUNT`.
- **Both ownership commands are clean, deterministic, lockstep-orderable,
  with no UI/local-state coupling.** `makeGameAddPlayerCmd` applies at
  `0x9d77fa` -> `createPlayer`, writes the new entity id into
  `resultEntity`. `makeEntitySetPlayerCmd` executes at **`sub_9db080`**: it
  checks both entities are alive, then does a **generic `PlayerOwned`
  write, with no branch on entity kind** (a negative player id removes the
  component). This is a real improvement over TPF2, where native
  `setPlayer` hit an assert and crashed on vehicles.
- **Company mechanics are Lua game-script state**, not native:
  `CompaniesState` / `CompanyState` and `company_util`
  (`getCompanyState`/`setCompanyState`/`externalGet*`) have no native
  symbols. Rank, permits, prospection and HQ live there. Only
  `headquarters_util::CompanyValue` is exposed to Lua as a native value. So
  the company layer is patchable and observable from a mod, while raw
  ownership and money are native and written only through the two ordered
  commands.
- **No documented player-count limit.**

Risks to measure in-game:
1. **`LineSystem` has a compiled-in assert on `PlayerOwned` changes**
   (`ecs::LineSystem::vf6`/`vf7`, `0xacf6b0`/`0xacf7e0`): reassigning a
   line's owner may route through it and trip. Highest priority.
2. **`resultEntity` determinism**: does `makeGameAddPlayerCmd` allocate the
   same entity id on every lockstep client (entity-id order under
   concurrent commands)?
3. `setPlayer` per entity kind (station, line, vehicle, depot, signal): the
   executor is uniform, but `PlayerOwned` change handlers fan out per
   system, so side-effects may differ.
4. A "bare" player (`headquarters=-1`, no `CompanyState`) may be
   inconsistent to `company_util`; the HQ/company Lua flow must run too.
5. Scale (finance/AI/UI were built for few companies) and save migration
   (`CompaniesState.version`).

## The script API (DOCUMENTED, from the on-disk `.d.tl`)

Full extraction is in
[TF3_OFFICIAL_API_2026-09-29.md](TF3_OFFICIAL_API_2026-09-29.md); the
on-disk declarations confirm and correct it:

- **61 `make*Cmd` factories confirmed** (55 production + 6 under
  `Cmd.debug`). Corrections: `makeWorldBuildProposalCmd`'s argument order is
  `(proposal, context, ignoreErrors, playerInitiated, doDust?)` -- the web
  reference had `doDust` and `playerInitiated` swapped -- and it is
  **overloaded** (a second signature takes a `SimpleProposal`). There is
  also a 62nd command factory, `makeSimPersonSetHappiness` (debug), whose
  name does not end in `Cmd`.
- **Both `getNode2StreetEdgeMap` and `getNodeSegments` exist** on
  `StreetSystem` (plus `getNode2SegmentMap`, `getNode2TrackEdgeMap`). Our
  `engine.lua` uses `getNode2StreetEdgeMap` (street edges only), which is
  valid; `getNodeSegments(node)` returns all segments for one node.
- `BASE_EDGE` fields (`node0/node1`, `position0/position1`,
  `tangent0/tangent1`, `type`, `typeIndex`, `objects`, `laneConfigs`,
  `roadType`), the `Proposal`/`SimpleProposal` shapes, the `Line`/`Stop`
  fields (with `reservationPriority`), and the game-script contract
  (`update`/`postUpdate`/`handleEvent`/`guiUpdate`, `state:get/set/
  subscribeToEvent`) are as recorded there.
- **`GAME_TIME.gameTime`'s unit is not declared** -- our "milliseconds" is
  an unverified TPF2 carryover. `timeOfDaySec` is seconds and
  `GameSpeed.millisPerDay` is ms, both explicit; `gameTime` is not.
  `tickCount` advances while paused, `updateCount` does not -- relevant to
  a lockstep clock. Confirm the unit in-game.

- Game scripts exist: 38 shipped `*.gs.lua` resources name `update`,

  without an entry in `mod.json`, and their state is a component on an

Who sends what:

- **Native tools do not go through Lua.** Roads, tracks, stations, the
  bulldozer, terraforming and the other placement tools are native handlers;
  `makeWorldBuildProposalCmd` has 13 native call sites, all passing 1 for the
  flag believed to be `playerInitiated` (INFERRED; measure it).
- **Script GUI commands share one sender.** Buying vehicles, lines, colours,
  names, loans and most panels send through one helper
  (`gui/main/engine_react_util.tl`). CONFIRMED-static.
- **Scripts see native builds.** GUI scripts get `builder.proposalCreate`,
  `proposalPrepareForApply` and `proposalApply` with the tool's id
  (`streetBuilder`, `trackBuilder`, `constructionBuilder`, `bulldozer`), and
  may return errors that refuse a build (`company.script.tl:559-603`).
  CONFIRMED-static that they are called; whether an error stops a native
  tool is to measure.

  `mods\`, `staging_area\`, `settings.lua`, `crash_dump\`, and others.
  MEASURED (the log names it).
- **The log** is `local\crash_dump\stdout.txt`, not `local\stdout.txt`.
  Lines read `[time - LEVEL - thread - subsystem]  message`, UTC, out of order
  across threads. `crash_dump\error.json` is a heartbeat the game rewrites
  while it runs, holding the Steam user id, a session id and hardware details.
  MEASURED.
- **Mods** are named by `modId` in `mod.json`, not by folder (folder
  `urbangames_sandbox` is `urbangames_sandbox_1`), and logged as `<modId>:
  modHubId=<source>,<path>`. The game knows four mod roots (dlc, mod,
  staging, userdata) and an `externalModPath` setting. `mod.json` holds
  `modId`, `revision`, dependencies, incompatibilities, options, params, and
  the pre-run, run and post-run scripts; `_metadata\modinfo.json` the name
  and authors. Campaign mission 07 says `cosmetic: true` and changes the
  economy: never trust `cosmetic`. CONFIRMED-static.
- **Saves**: one plain zstd stream per `.sav`, no wrapper; unpacked it starts
  `tf**` like TPF2's. The 12 saves shipped with the game are 20-87 MB
  compressed, 71-234 MB unpacked. **There is no `.sav.lua` sidecar**: the mod
  list, map settings, mod params and script state are inside the save, script
  state as binary tables (no Lua source or bytecode found). The header holds
  a version (596-604; the running game reports 604), the start year, the map's
  size, the date and a 640×360 thumbnail (INFERRED but the magic). Names:
  `autosave_`, `crashsave_`, `exitsave_`.
- **Timings** (this PC, one run): 11 s to the main menu; a new Very Large map
  in 75.6 s. MEASURED.
- **Steam restart**: this run started once, and the executable has no
  `RestartAppIfNecessary` string. But Steam started this run, so it does not
  answer whether a game the launcher starts restarts itself.
- mod.io's game id for TF3 is likely 10640 (a folder of that name appeared at

- `crates/tpf3mp-launch`: `TransportFever3.exe` is right; its TODO can go.
- `tools/tpfre`: the assert and profiler names as a naming source.
- `tools/dayone/dayone.py scripts`: its report quotes the game's source lines;
  it should cite file and line only, as the report committed here does.

**For the owner.** These change the plan's design. Flagged, not settled:

1. **`playerInitiated` reaches the simulation.** The engine hands it to game
   scripts with every build (`towns.script.tl:271`), and only player-initiated
   builds change a town's reputation (`town_util.tl:1065`). A replay must carry
   the original value, so it cannot also mark our replays, and the idea,
   recorded earlier in `TF3_OFFICIAL_API_2026-09-29.md`, of telling a
   replay apart by it does not hold.
2. **The caller-address filter covers native tools only.** Builds from the
   native tools come from native call sites and can be told apart by caller
   (HOOKS.md); script GUI commands all leave through one Lua helper, the same
   path our replays take through `api.cmd.sendCommand`. Those need another
   way to be told apart (PLAN Part 2, the last Dev A item).
3. **Hooking `CommandList::Add` alone misses game-script commands**,
   which are applied without it; the hook belongs at the apply
   (`0x9e1c10`).
4. **The speed.** The GUI lowers the speed to what the local machine can do,
   every step, and a simulation script sets speed 1 when a game starts. In a
   room the hook must drop the game's own speed commands and apply the
   room's. `setDisableFeatures` with `GameSpeedControl` and `GameSpeedPause`
   hides the buttons and keys (it replaces the whole table). Calendar speed,
   time of day and weather are also every player's to change; calendar speed
   changes the simulation, so the room should own it.
5. **One player in the game's economy.** Companies, loans and subsidies book
   to `getPlayer()`, and a loan's amount comes from the GUI. That touches D6
   (the game's own economy) and Part 3's companies, loans and subsidies.
6. **Random state is not saved**, game scripts' `update()` runs in
   parallel on per-thread Lua states, and the town development's `rand()`
   is seeded from the clock. Late join, rejoin and repair all load a save, so
   Test A's rejoin case meets this first. The hook may need to seed `rand()`
   and the script states from the room.
7. **No `.sav.lua` sidecar.** Part 2's `save_check::check_lua_data` on a
   fetched save has nothing to check; a check before loading would read the
   save's header instead.
8. **Save sizes.** SNAPSHOTS.md assumes 50-500 MB saves; they are 20-87 MB
   and already zstd-compressed, so chunking the compressed file dedupes
   poorly. Chunking the unpacked data is the likely fix (INFERRED).

### The questions the static passes left open

Settled in the executable, CONFIRMED-static unless marked. Two claims
above are corrected here: the second command sink, and `mt19937`.

- **The world queue is `CommandList::Add`** on `CGame+0x1e8`; `Swap`
  hands it over and `RunGameSimLoop` applies it (at `0x11eb96`).
  `DeferredCommandBuffer` is a render buffer and never reaches the apply.
  `sub_e42470` only pushes a `Command` onto the Lua stack. The script
  `sendCommand` is `0xe2a190`, and it calls the sink its Lua state was
  registered with.
- **Game-script commands never pass `Add`.** GUI states send through
  `Add`. Game scripts:
  - their `update()` runs **in parallel** on a thread pool
    (`GameScriptSystem::Update`, `0xaaf350`); each script's commands go
    to a buffer of its own and are applied after the loop, in script
    order, straight through the apply (`0x9e1c10`, from `0x268ed0`), their
    callbacks dropped;
  - `postUpdate`, `handleEvent` and other sends on the simulation thread
    apply at once through the sink `0x120410`.

  The apply has exactly four callers (`0x11eb96`, `0x1204bf`, `0x268ed4`,
  and `0x120334` in a sink the `CGame` constructor builds and discards,
  likely dead: INFERRED). **A hook at `0x9e1c10` sees every command; one at
  `Add` misses the game scripts'.**
- **`playerInitiated` in the command** is the byte at payload `+0x3d2`
  (`ignoreErrors` `+0x3d1`, `doDust` `+0x9b0`, an unknown bool `+0x3d0`
  that Lua always sets). It is read in the build handler (`0x9e1160`, at
  `0x9e157f` and `0x9e18ac`) and handed to the scripts' pre- and
  post-build events. All 16 native call sites (in 14 functions) pass 1 and
  then call `Add`.
- **Lua states.** Every state comes from one constructor (`lua_newstate`
  `0x2fc13d0`). Game scripts get **one state per OS thread** for each API
  type, not one per script and not one shared. Scripts are kept in a tree
  keyed by resource name (INFERRED, strong), so the buffered commands and
  `postUpdate` run in name order; `update()` has no order; which thread,
  and so which state, runs a script depends on scheduling (INFERRED).
- **The string-hash seed is random.** `makeseed` (`0x2fc1690`) is Lua
  5.2.2's own, mixing `_time64`, heap and stack addresses. So `pairs` order
  over string keys can differ between two games, and between two states of
  one game; the live probe saw it stable only within one state.
- **`math.random`** is a `boost::random::mt19937` per Lua state (the
  tempering is there, rewritten; the earlier "no `mt19937`" was wrong),
  seeded with the constant 5489 when a state is made, and reseeded by the
  engine only for some events and helpers, not for `update()` or
  `postUpdate()` (INFERRED). It is not saved (INFERRED). With one state per
  thread, a script's draws depend on which thread ran it before.
- **`rand()` has exactly four call sites** (no address taken): the town
  development handler (`0x9df3ac`, on the simulation thread), Mod Hub
  staging, and the stock `math.random` the game replaces. The first is the
  only one in the simulation.

What this means (INFERRED, to measure with two games): the game's own
scripts, as the engine runs them, are unlikely to agree between two games.
The room probably needs the game scripts on one thread, their random
state seeded from the room, and the capture at the apply, not only at
`Add`. Still UNKNOWN: the API types' names and which one game scripts
use, the byte at `+0x3d0`, and the `handleEvent` order.
